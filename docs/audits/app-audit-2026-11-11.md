## Hallazgos

### F01 · P1 · Cambiar la contraseña no invalida los refresh tokens anteriores

**Reproducido por HTTP.** `packages/backend/src/routes/v1/auth.routes.ts:234`
actualiza el hash sin eliminar los refresh tokens. `AuthService.refresh` emite
después un JWT vinculado al hash nuevo. El JWT anterior sí se invalida, pero
quien conserva su refresh token recupera acceso sin conocer la nueva contraseña.

Secuencia en una base nueva:

1. Registrar un usuario y conservar su refresh token.
2. Cambiar la contraseña mediante `/auth/change-password`: HTTP 200.
3. Usar el refresh token previo en `/auth/refresh`: HTTP 200.
4. Usar el nuevo access token en `/auth/me`: HTTP 200.

El restablecimiento administrativo ya revoca refresh tokens; este flujo no.
Corregir ambos cambios de forma atómica y definir cómo vuelve a autenticarse
la sesión que hizo el cambio. Añadir regresión HTTP con dos sesiones.

### F02 · P1 · La app exporta respaldos que su API no permite restaurar

**Reproducido por HTTP.** Las rutas de preview/import no configuran un límite de
cuerpo adecuado (`packages/backend/src/routes/v1/backup.routes.ts:61,101`);
`server.ts` tampoco lo modifica. Los adjuntos se incluyen como base64 en el JSON
(`services/backup.service.ts:160`), mientras la subida permite archivos de hasta
10 MiB (`routes/v1/attachments.routes.ts:59`).

Con un único adjunto sintético de 900.000 bytes, el export produjo un JSON de
1.204.010 bytes y HTTP 200. Enviar ese mismo respaldo a preview e import devolvió
**413, Request body is too large**, antes de procesarlo. La reproducción usó el
servicio de almacenamiento para crear el adjunto; no evaluó el contenido OCR.

Definir límites coherentes de export/import y una estrategia para respaldos
grandes (por ejemplo, archivo multipart y procesamiento acotado). No desactivar
límites globalmente. Probar exportación/restauración por HTTP con varios adjuntos,
y un rechazo explícito y comprensible cuando se supere el límite soportado.

### F03 · P2 · Un scope desconocido crea una API key sin restricciones

**Reproducido.** `validators/auth.schema.ts:72` permite cualquier cadena;
`config/scopes.ts:69–72` descarta valores desconocidos y convierte un resultado
vacío en `null`, que significa acceso completo.

Crear una clave con `scopes: ["read:acounts"]` devuelve 201 y sus permisos efectivos
son `null`. Un error de escritura puede ampliar los privilegios sin advertencia.
No permite que una clave restringida existente escale por sí sola: el problema
es la creación de la clave por un usuario autorizado.

Rechazar scopes desconocidos con 422, conservando la intención explícita de crear
una clave completa cuando corresponda. Probar listas inválidas y mixtas.

### F04 · P2 · La expiración solicitada para una API key se ignora

**Reproducido.** `validators/auth.schema.ts:74` acepta `expiresAt`, pero
`routes/v1/api-keys.routes.ts:54` no lo transmite al servicio. La tabla y la
validación de claves no implementan esa caducidad.

Una clave solicitada con `expiresAt: "2000-01-01T00:00:00Z"` se creó con 201 y
fue aceptada por `AuthService.validateApiKey`. Es un contrato de API engañoso,
aunque el formulario actual no ofrezca seleccionar caducidad.

Implementar almacenamiento y comprobación de expiración, o rechazar expresamente
esa opción mientras no se soporte; nunca aceptarla y descartarla en silencio.

### F05 · P2 · Los sensores de Home Assistant mezclan monedas sin conversión

**Reproducido en `/ha/status`; la misma lógica aparece en `/ha/sensors`.**
`routes/v1/ha.routes.ts:46,60,88` suma cantidades y saldos sin tipos de cambio,
pero publica `currency` como la moneda base. La duplicación aparece también en
las líneas 277, 291 y 318.

Caso: base MXN, cuenta USD con saldo inicial 1.000, cambio 20 y gasto de 100 USD.

| Campo | Respuesta | Valor esperado en MXN |
| --- | ---: | ---: |
| monthly_expenses | 100 | 2.000 |
| consolidated_balance / total_balance | 900 | 18.000 |
| top_categories[0].total | 2.000 | 2.000 |
| net_worth | 18.000 | 18.000 |

El propio payload resulta inconsistente. Reutilizar los agregados convertidos
de reportes/cuentas, y publicar la moneda correcta para sensores por cuenta.
Probar ambos endpoints con dos monedas y la integración consumidora.

### F06 · P2 · El add-on ignora BACKUP_ENABLED=false

**Reproducido con jq en la imagen HA local.** `ha-addon/run.sh:18` usa
`.BACKUP_ENABLED // true`. En jq, `//` sustituye también el booleano `false`.
La entrada `{"BACKUP_ENABLED":false}` devuelve `true`, por lo que desactivar
respaldos desde las opciones no tiene efecto.

Aplicar el valor por defecto únicamente cuando el campo esté ausente o sea null.
Probar true, false y ausencia de configuración en el script de arranque.

### F07 · P2 · La lista de sesiones no reconoce la sesión actual del navegador

**Reproducido por HTTP y contrastado con la UI.** El cliente envía el marcador
`cookie` como query (`frontend/src/lib/api/auth.ts:145–146`). El servidor pasa
esa cadena directamente a `listSessions` (`routes/v1/auth.routes.ts:348–349`),
que la compara con el token real (`services/auth.service.ts:741`). El helper
`apiGet` tampoco añade la cabecera de sesión de navegador.

Incluso enviando una cookie válida y la cabecera de navegador en la reproducción,
la única sesión devuelve `current:false`. En Configuración desaparece la marca
de sesión actual y no se ejecuta la rama que redirige al login al revocarla
(`frontend/src/routes/(app)/configuracion/+page.svelte:430`).

Resolver el token HttpOnly en el servidor con el contrato de sesión del cliente;
no volver a exponerlo en la URL. Probar identificación y revocación desde la UI.

### F08 · P2 · Los reportes personalizados no viajan en el respaldo JSON

**Reproducido.** `CustomReportService` persiste los reportes guardados en
`custom_reports`, pero `BackupService.export` no incluye esa tabla y el
importador tampoco la restaura.

Crear un reporte llamado “Saved audit report” devuelve una lista con un elemento;
el respaldo exportado no contiene ese reporte. Al migrar a una instancia nueva
no se recupera, pese a que se ofrece un respaldo de los datos del usuario.

Agregar la entidad al contrato compatible de export/import/preview, respetando
propietario y remapeo de referencias dentro de su configuración. Probar el ciclo
completo con un usuario destino distinto.

### F09 · P3 · Los cambios solo en idiomas no activan la matriz desktop

**Revisión estática.** `.github/workflows/desktop-build.yml:6–9` filtra PRs por
`packages/**`, `package*.json` y el propio workflow. No incluye `locales/**`,
los scripts generadores ni la configuración HA que necesita `locales:check`.
Cambiar solo el texto de un JSON puede no cambiar archivos generados dentro de
`packages`, porque estos importan el JSON, y por tanto no activa este workflow.

La CI general sí verifica idiomas y compilación web, pero no reemplaza la matriz
de empaquetado por sistema operativo. Ampliar paths a las entradas reales de la
compilación desktop.

### F10 · P3 · La auditoría de producción omite avisos de la cadena frontend

**Resultado actual de npm audit.** El audit completo del monorepo informa seis
entradas de severidad baja derivadas de **tres avisos**, no seis fallos independientes:

- [SvelteKit: redirección en formularios mejorados](https://github.com/advisories/GHSA-pfhg-q3qv-9q6r).
- [SvelteKit: cache-control no confiable en prerender](https://github.com/advisories/GHSA-27mw-82g8-phjj).
- [deepmerge: contaminación de prototipos](https://github.com/advisories/GHSA-gcqx-w48m-w2h4).

`npm audit --omit=dev` devuelve cero: SvelteKit y el adaptador están declarados
como herramientas de desarrollo, aunque participan en el artefacto servido.
No se encontró uso de `use:enhance` ni `setHeaders` con cache-control no confiable
en el código revisado; no se demostró explotación de estos avisos en HomeLedger.
El aviso de deepmerge no anuncia una versión corregida.

Revisar alcance real y actualización compatible de la cadena frontend; npm
propone cambios mayores para parte de ella. Incorporar revisión del audit completo
a CI sin aplicar automáticamente `audit fix --force` ni atribuir protección total
al resultado de `--omit=dev`.

## Seguimiento de correcciones

- **F01 resuelto:** el cambio de contraseña usa la misma transacción de revocación
  que el reset administrativo. Invalida los JWT vinculados al hash, elimina todos
  los refresh tokens y la cookie, y devuelve el navegador al login. El mínimo
  de ocho caracteres coincide en backend e interfaz, en los tres idiomas.
- **F02 resuelto:** exportación, previsualización e importación comparten un límite
  de JSON de 32 MiB; solo las rutas de respaldo amplían el límite HTTP. Se rechazan
  archivos demasiado grandes antes de leer sus binarios y se informa del respaldo
  de volumen como alternativa. La guía de proxy permite 33 MiB para el sobre JSON.
- **F03 resuelto:** scopes desconocidos o mezclados con válidos se rechazan, sin
  convertir una errata en acceso total. Omitir scopes o enviar `[]` conserva el
  contrato explícito de acceso completo.
- **F04 resuelto:** migración `0018_api_key_expiry`, validación de fecha futura,
  persistencia, metadatos y rechazo de claves vencidas. Las claves anteriores
  mantienen `expiresAt: null`. La API de creación acepta `expiresAt` ISO opcional.
- **F05 resuelto:** ambos endpoints HA convierten ingresos, gastos y saldo agregado
  a moneda base. Los sensores de cuenta conservan saldo y unidad nativos; los de
  categoría conservan la moneda base.
- **F06 resuelto:** el arranque HA conserva `BACKUP_ENABLED=false`. Solo un valor
  ausente o `null` toma el valor predeterminado `true`.
- **F07 resuelto:** la lista de sesiones resuelve la cookie HttpOnly del navegador;
  el cliente ya no transmite el marcador en la URL. La prueba verifica una sola
  sesión actual entre dos sesiones activas.
- **F08 resuelto:** los reportes guardados se exportan, validan y restauran dentro
  de la transacción. Se reasignan referencias de configuración a los IDs nuevos;
  se conserva aislamiento entre usuarios y compatibilidad con respaldos antiguos.
- **F09 resuelto:** el workflow desktop incluye paquetes de idioma, sus scripts,
  configuración HA y TypeScript base entre sus disparadores.
- **F10 parcialmente resuelto / residual upstream:** SvelteKit 3, adapter-node 6,
  plugin 7, Vite 8 y TypeScript 6 del frontend sustituyen la cadena anterior.
  Se adaptaron configuración, navegación reactiva, imports y service worker.
  Los dos avisos propios de SvelteKit desaparecen. Queda **un aviso bajo de
  deepmerge**, reflejado en cuatro entradas transitivas del árbol de desarrollo.
  [Upstream no publica una versión corregida](https://github.com/advisories/GHSA-gcqx-w48m-w2h4).
  El uso inspeccionado en `vite-plugin-svelte` mezcla configuración local de build,
  no entradas de usuarios. No se rebajó a una versión antigua ni se ocultó con
  `audit fix --force`. CI revisa ahora el árbol completo, permite únicamente ese
  aviso bajo en paquetes `dev`, y falla ante otros avisos o exposición en runtime.
  Retirar la excepción de `scripts/check-dependencies.mjs` al publicarse una solución.

La migración sigue la [guía oficial de SvelteKit 3](https://svelte.dev/docs/kit/migrating-to-sveltekit-3).
Requiere Node >= 22.17 para desarrollo. También se corrigieron los selectores
`:global(...)` inválidos en el CSS externo de modales y la creación perezosa del
directorio de adjuntos; las carpetas de prueba se recrean entre casos.
