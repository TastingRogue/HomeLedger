# Auditoría de HomeLedger — 3 de noviembre de 2026

Seguimiento: [correcciones y pruebas actuales](AUDIT-FIXES.es.md).
Los hallazgos siguientes describen la base v1.2.0 previa a esas correcciones.

Base: release v1.2.0, main. Revisión de código, despliegue, documentación y avisos
de dependencias. No se modificó la lógica ni se publicaron correcciones.

## Hallazgos priorizados

### Alta — imágenes rotas en GitHub Pages

`docs/index.html:257,302–327` referencia seis imágenes eliminadas: dashboard.png,
transactions.png, budgets.png, goals.png, receipts.png y subscriptions.png.
La portada pública responde HTTP 200 y transactions.png responde HTTP 404.
El workflow de Pages publica correctamente docs/: el fallo está en las rutas,
no en el despliegue. El diff desde v1.1.3 conserva las secciones del HTML;
solo cambió la versión. Al limpiar capturas se sustituyeron los archivos por JPG
sin actualizar esta página.

Actualizar tanto src como href a los JPG disponibles, incorporar Cyberpunk y
añadir una comprobación automática de referencias locales antes del despliegue.
El README ya usa las capturas nuevas; la landing quedó desactualizada.

### Alta — avisos en dependencias de producción

`npm audit --omit=dev`: 9 paquetes afectados, 3 altos y 6 moderados, cero críticos.
Altos: fast-uri, sharp y zod. Moderados: fastify, ip-address, @fastify/static,
@fastify/swagger-ui, glob y minimatch. Es un informe de dependencias, no una
demostración de explotación en HomeLedger.

Priorizar actualizaciones compatibles y comprobar importación, validación de
entrada, OCR y OpenAPI. No aplicar `npm audit fix --force` sin revisar: para
parte del árbol npm propone cambiar de versión mayor de swagger-ui.

### Media — CORS permisivo por defecto

`packages/backend/src/server.ts:61–65`: sin CORS_ORIGIN se refleja cualquier origen
y se habilitan credenciales. Las rutas privadas conservan autenticación, por lo
que no se ha demostrado acceso anónimo a datos. Configurar orígenes explícitos
en producción y estudiar un valor por defecto más restrictivo.

### Media — tokens persistidos en localStorage

`packages/frontend/src/lib/stores/auth.ts:24–49` y `lib/api/client.ts:34–49`:
access y refresh tokens son accesibles desde JavaScript. Una eventual XSS podría
leerlos; no se encontró ni explotó una XSS en esta revisión. Evaluar refresh en
cookie HttpOnly/Secure, política CSP y pruebas de renovación/cierre de sesiones.

### Media — contenedor ejecutado como root

El Dockerfile no declara USER. Establecer un usuario sin privilegios y verificar
permisos del volumen, SQLite, backups y OCR al actualizar instalaciones existentes.
Tampoco declara HEALTHCHECK: añadir una comprobación del endpoint de salud.

### Media — cobertura de regresión visual y de Pages

La CI cubre tipos, lint, pruebas, build y bootstrap de temas. La pérdida de imágenes
demuestra que falta comprobar recursos del sitio. Las validaciones responsive
anteriores fueron manuales y no sustituyen pruebas E2E persistentes para ambos
temas, navegación móvil, filtros, popups y formularios largos.

## Evidencia favorable

- Release v1.2.0: 717 pruebas backend/shared y 137 frontend aprobadas; typecheck,
  build y comprobación de temas aprobados en la validación previa del release.
- CI y publicación Docker AMD64/ARM64 finalizaron correctamente para ese release.
- Pages usa HTTPS y un workflow que publica docs/; los últimos despliegues
  consultados terminaron correctamente.
- Autenticación y scopes centralizados; respuestas privadas excluidas de la caché
  del service worker; JWT_SECRET requerido en Compose; dependencias fijadas por
  lockfile; estilos responsive nuevos limitados al tema Normal.

## Límites y siguiente validación

Esta auditoría no certifica ausencia de vulnerabilidades. No se repitió la suite
completa ni cada flujo UI en esta pasada; los resultados de pruebas anteriores se
identifican como evidencia del release. Quedan pendientes pruebas E2E actuales
en ambos temas, aislamiento entre usuarios, restauración real de backups en un
volumen desechable, OCR/importaciones con entradas adversas, carga de historiales
grandes y una instalación real de Home Assistant. El envío de webhooks necesita
revisión específica de destinos privados, DNS y redirecciones antes de emitir un
dictamen sobre SSRF. No se realizaron acciones destructivas sobre los datos demo.

Orden recomendado: reparar Pages, actualizar dependencias con regresiones,
endurecer despliegue y sesiones, y ampliar la cobertura E2E. Estado: pendientes
antes de considerar cerrada la auditoría integral.
